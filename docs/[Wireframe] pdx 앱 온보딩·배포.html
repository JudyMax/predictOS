1. 목표와 사용 맥락

사용자Application Manager는 등록·재제출·자기 앱 현황 확인을, Platform Admin은 검토·배포·권한 관리·변경 기록 조회를, Plant Operator는 자기 공장 상태 확인과 사용 권한 요청을 맡는다. [S1] [S3]
목표흐름 1: 새 버전을 승인받아 공장에서 정상 동작시킨다. 흐름 2: 쓸 수 없는 앱의 사용 권한을 얻는다. 흐름 3: 사용자의 앱 접근을 제때 부여·제한한다. 흐름 4: 누가 언제 무엇을 승인·배포했는지 확인한다. [S1]
진입모든 흐름은 고객사 pdx 화면 안에서 시작한다. LNB 위쪽 메뉴 4개(앱 버전 관리·배포 관리·권한 관리·변경 기록)와, 같은 LNB의 구분선 아래 공장 목록(공장 전환 영역)에서 여는 공장 화면이 진입점이다. 흐름 1-B는 승인된 버전의 '배포하기'에서 시작한다. [S7] [S4] [S6]
선행 조건사용자는 pdx 공통 계정과 역할을 이미 가지고 있다. 공장(Workspace) 등록과 계정 생성은 이번 범위 밖이므로 이미 되어 있다고 본다. [S5]
범위앱 20개 × 공장 3곳에 같은 절차를 적용한다. 고객사·외부 업체 앱, 공장 등록·계정 생성, 반려 사유를 원프레딕트에 전달하는 일, 제출 철회, 검토 대기 장기화 알림, 앱 자체 화면은 제외한다. [S1] [S3] [S6]
종료배포는 공장별로 완료 또는 실패 상태가 보이면 끝난다. 사용 권한 요청은 요청자가 공장 화면의 앱 행에서 결과를 보면 끝난다. 두 경우 모두 외부 알림(메일·문자)은 보내지 않는다. [S2] [S6]

2. User Flow

역할별 행동과 시스템 반응, 분기만 그렸다. 흰 사각형은 사람의 행동, 회색 점선 사각형은 시스템 반응이고, 대괄호 안은 행동하는 역할이다. 검은 '기록' 표지는 변경 기록이 자동으로 남는 지점이다(REQ-BE-AUDIT-003). 굵은 점선은 근거 없는 제안이다. 흐름 검토 코멘트 4건을 반영했다. [S1] [S8]

시작·종료사용자 행동시스템 반응조건 판단기록 지점제안

흐름 1-A. 새 버전 등록·검토

  1. Application Manager가 패치 파일을 제출한다(재제출도 같은 행동이다). REQ-FE-REG-001, REQ-BE-APRV-007 [S1]
  2. 시스템이 패치 파일 안의 등록 정보를 자동으로 읽는다. 사람은 등록 정보를 입력하거나 고치지 않는다. REQ-BE-REG-005, POL-007 [S2]
  3. 필수 항목이 빠졌거나 형식이 틀리거나, 버전 규칙(승인된 최신 버전보다 높을 것, 이전 버전은 승인된 버전이며 새 버전보다 낮을 것)을 어기면 등록 데이터 검증 실패다. 저장하지 않으므로 등록 상태도 생기지 않는다. 어긋난 항목을 표시하고, Application Manager는 파일을 고쳐 1로 돌아간다. REQ-BE-REG-002·003·006, POL-010·061~063 [S1] [S2]
  4. 검증을 통과하면 승인 대기로 저장하고 기록을 남긴다. Platform Admin이 검토한 뒤 승인이나 반려를 고른다. 자신이 제출한 등록은 승인할 수 없다. REQ-BE-REG-001, REQ-BE-APRV-002, REQ-BE-AUDIT-003 [S1]
  5. 그 사이 다른 Admin이 먼저 처리했다면 시스템이 거부하고 먼저 처리된 결과를 유지한다. 이미 처리됐다는 안내와 최신 상태를 보여 주며 승인·반려 버튼을 비활성화한다. POL-064, REQ-BE-APRV-008, REQ-FE-APRV-005·006 [S1] [S2]
  6. 승인하면 승인됨으로 등록이 확정되고 기록을 남긴다. 승인된 버전은 흐름 1-B에서 공장을 고르고 사전 환경 검증을 통과해야 배포할 수 있다. REQ-BE-APRV-001·003 [S1]
  7. 반려하려면 사유를 반드시 입력해야 한다. 반려 상태가 되고 기록을 남기며, 결과와 사유는 제출자에게만 보인다. Application Manager는 사유를 확인한 뒤 고친 파일로 1부터 재제출한다. 제출 철회는 MVP 범위 밖이다. REQ-BE-APRV-004~007, WG-04 [S1] [S6]

흐름 1-B. 공장별 배포·정상 동작 확인

  1. Platform Admin이 승인된 버전의 '배포하기'로 들어와 대상 공장을 고른다. REQ-FE-DEPLOY-007·001 [S1] [S4]
  2. 시스템이 공장마다 독립으로 사전 환경 검증을 한다. 버전 검사(pdx 버전 → MxFM 버전 → 업그레이드 경로)를 먼저 하고, 그다음 설정 검사(권한·데이터 연결)를 한다. REQ-BE-DEPLOY-003·007 [S2]
  3. 검증 결과는 저장하지 않는 임시 결과다. 버전 충돌이면 필요한 선행 버전과 해결 방법을 안내하며, Admin은 선행 버전을 먼저 배포한 뒤 1부터 다시 진행한다(WG-03). REQ-BE-DEPLOY-008, POL-026 [S2] [S6]
  4. 설정이 부족하면 부족 항목을 한 번에 모두 표시한다. Admin이 채우면 다시 검증한다. 점검 단계의 차단은 배포 이력이 아니므로 기록·알림하지 않는다. 점검이 끝날 때마다 성공 지표 집계용 점검 로그만 남는다(화면에 보이지 않음). REQ-BE-DEPLOY-005·009·021, POL-065·066 [S1] [S2]
  5. Admin이 통과한 공장의 일괄 실행을 확인하면(WG-02) 그때 배포 이력을 만들고 실행 직전 점검 결과(검사 ①~⑤별 통과 여부와 비교한 두 값)를 스냅샷으로 함께 저장한다. 시스템은 설치 중 → 동작 확인 중으로 상태를 바꾸고 배포 실행을 기록한다. 이 확인이 '선택·검증'과 '실행·이력'의 경계다. REQ-BE-DEPLOY-012·015·022, POL-030·067 [S1] [S2]
  6. 배포 후 정상 동작 확인 기준을 충족하면 완료로 새 버전이 반영되고 기록을 남긴다. 시간 기준은 정책을 따른다(POL-032). REQ-BE-DEPLOY-016 [S2]
  7. 기준을 충족하지 못하면 실패로 이전 버전을 그대로 유지하고, Admin과 그 버전의 등록자에게 알림함·배너로 알리며 기록을 남긴다. 자동 재시도는 없고, 실패한 버전은 그 공장에 다시 실행하지 않는다. Application Manager가 원인을 고친 새 버전을 등록해 흐름 1-A부터 다시 거친다. 알림을 누르면 Admin은 배포 관리로, Application Manager는 버전 상세로 간다(WG-11). REQ-BE-DEPLOY-017~019, REQ-FE-DEPLOY-008~011, POL-033·034 [S1] [S2] [S6]
  8. 모든 역할이 공장 화면에서 공장별 상태를 확인한다. Admin은 모든 공장, Operator는 자기 공장만 본다. Application Manager는 앱 버전 관리에서 자기 앱의 공장별 현황도 본다. REQ-FE-STAT-001~005, WG-07 [S1] [S6]

흐름 2. 사용 권한 요청

  1. Plant Operator가 공장 화면에서 사용 권한이 없는 앱을 누르면, 시스템이 사용 권한을 요청하라는 안내를 보여 준다. WG-08 [S6]
  2. Operator가 사유를 입력해 요청한다. 공장은 요청자의 소속 공장으로 정해진다. REQ-BE-ACCT-005 [S1]
  3. 같은 앱에 처리 대기 중인 요청이 이미 있으면 새 요청을 거부한다. 처리 대기 상태가 아닌 요청은 다시 승인·거절할 수 없다. REQ-BE-ACCT-006·011, POL-068 [S1] [S2]
  4. Platform Admin이 권한 관리의 '사용 권한 요청' 탭에서 승인하면 즉시 사용 권한을 주고, 처리자·대상·변경 전후 값·사유·시각을 기록한다. REQ-BE-ACCT-007, WG-09 [S1] [S6]
  5. 거절하려면 사유를 반드시 입력해야 하고, 요청은 거절됨이 되며 같은 항목으로 기록한다. REQ-BE-ACCT-008·009 [S1]
  6. 요청자는 공장 화면의 앱 행에서 결과와 사유를 확인한다. 외부 알림은 없다. REQ-BE-ACCT-010, WG-08 [S2] [S6]

흐름 3. 접근 권한 부여·제한

  1. Platform Admin이 사용자를 고르고 부여·앱 권한 제한·계정 전체 차단 중 하나를 고른다. REQ-FE-ACCT-001·002 [S1]
  2. 부여하면 그 사용자의 역할·접근 권한을 앱별로 추가한다. REQ-BE-ACCT-001 [S1]
  3. 앱 권한 제한은 그 앱의 접근 권한을 제거하고, 계정 전체 차단은 계정을 비활성화한다. 둘 다 이미 로그인한 세션에도 즉시 반영한다. REQ-BE-ACCT-002~004 [S2]
  4. 세 조치 모두 공통으로 처리자·대상·변경 전후 값·사유·시각을 변경 기록에 남기고, Admin은 처리 결과를 확인한다. REQ-BE-AUDIT-003, REQ-FE-ACCT-001·002 [S1] [S8] [S9]

흐름 4. 변경 기록 조회

  1. 사용자가 변경 기록을 연다. Platform Admin이 아니면 조회를 거부한다. REQ-BE-AUDIT-001 [S1]
  2. 시스템이 요청자·승인자·실행자·반영 시점이 담긴 기록을 보여 주고, 조회자와 조회 시각도 기록에 남긴다. REQ-FE-AUDIT-001, REQ-BE-AUDIT-002 [S1]
  3. Admin이 기간·공장·앱·행위자·행위 유형으로 필터를 적용한다. 결과가 없으면 결과 없음을 안내하고 필터 초기화를 제공한다. REQ-FE-AUDIT-002·003 [S1]
  4. Admin은 기록 상세를 읽기 전용으로 확인한다. 기록은 누구도 고치거나 지울 수 없다. REQ-BE-AUDIT-004 [S2]
